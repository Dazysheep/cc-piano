# 任务队列与子进程进度协议

## 概述

cc-piano（琴房 Studio）采用「本地 HTTP 服务 + 串行任务队列 + 子进程执行」的调度模型。网页端不直接执行渲染，而是把任务参数落盘为 JSON，交由后台队列串行调度；每个任务由一个独立子进程执行，子进程通过逐行输出 `@@{json}` 形式的进度消息与父进程通信，父进程解析后供网页轮询。这一模式同时服务于渲染、转写、音轨剪辑、拨片开头等多条业务线，是软件架构的中枢。

## 架构位置

```
cc-piano.exe（app/launcher.py，PyInstaller）
  └─ 内置 Python 后台启动 web/server.py（ThreadingHTTPServer，仅监听 127.0.0.1:8765）
       ├─ 前端：web/app.html 外壳 + 各页面（单文件 HTML，无前端构建）
       ├─ 任务队列 job_queue（渲染/转写/音轨/拨片开头，串行执行，一次一个）
       │    └─ 每个任务 = 一个子进程：piano/render.py、tracks/build.py、tracks/flick_render.py、piano/transcribe.py
       └─ 发布队列 publish_queue（一次一个 Edge 发布窗口）→ publish/publisher.py
```

`web/server.py`（793 行）承载全部 HTTP 接口与任务队列，是队列与协议的实现主体。

## 任务队列（job_queue）

- **串行执行**：队列一次只运行一个任务，避免多个渲染子进程同时抢占 CPU 与内存（单进程连同 x264 编码约占 400–600MB）。
- **任务类型**：渲染（`piano/render.py`）、转写（`piano/transcribe.py`）、音轨剪辑（`tracks/build.py`）、拨片开头（`tracks/flick_render.py`）。
- **参数落盘**：网页 `POST /api/render` 后，参数写成 `uploads/jobs/<id>.json`，子进程以 `--job <json>` 读取，实现前后端解耦。
- **状态查询**：网页轮询 `/api/jobs/<id>` 获取任务状态与进度。

## 子进程进度协议

调用形式为 `piano/render.py --job <json> --json-progress`。子进程在标准输出上逐行打印 `@@{json}` 形式的进度消息，server 逐行解析，转换为任务进度供网页轮询。该协议的关键特征：

- **单向流式**：子进程只负责输出，父进程只负责解析，无需双向 RPC。
- **行分隔**：以换行切分消息，天然适配管道读取。
- **前缀标记**：`@@` 前缀用于从普通日志中区分结构化进度行。
- **JSON 载荷**：进度内容为 JSON，便于扩展字段（阶段、百分比、消息等）。

## 发布队列（publish_queue）

发布台使用独立的 `publish_queue`，一次只打开一个 Edge 发布窗口，由 `publish/publisher.py` 驱动。与渲染队列分离，避免长时间占用的渲染任务阻塞发布交互。发布流程为半自动：填好标题、文案、话题后停在「发布」按钮前由人确认，详见 [[半自动多平台发布]]。

## 设计权衡

- **串行 vs 并行**：队列层串行保证资源可控，真正的并行发生在渲染内部——`piano/render.py` 用 `multiprocessing.Pool`（默认 4 进程）对 10 秒切片并行渲染，详见 [[midi到下落音符视频渲染管线]]。
- **子进程隔离**：渲染崩溃或内存不足不会拖垮 server；失败片段在渲染内部自动重试一次。
- **本地单机约束**：服务仅监听 `127.0.0.1:8765`，端口可用环境变量 `QINFANG_PORT` 修改；端口被占用时视为琴房已在运行，直接打开页面。
